Status: recommendations for discussion, not approved scope or a production start. Playai source baseline: 861f2c4. Doplay HEAD verified through GitHub as c36c39182e010df38eda9e51c5acc237673c7bac; source inspected with git show at that revision. ## Recommended decisions before implementation

1. Reconcile the production baseline with accepted prototype behavior. README/ROADMAP still describe one game and the architecture's join cap is eight, while the prototype explores four games and up to twenty players. Select launch scope and game-specific supported group sizes explicitly. Preserve the existing server-owned state and room/game boundaries; implementing the latest mockup must not silently override production gates.
2. Define one room lifecycle table: disconnect versus intentional leave, host transfer grace, reconnect identity proof, refresh, duplicate tabs, late joining, insufficient active players, room expiry, abort and return to results. The current local background pause cannot become a shared-game pause for everyone.
3. Define each waiting phase's deadline and timeout outcome. In particular: absent clue giver, missing Bluff answer/vote, host unavailable during Categories review. Decide who can advance and whether an incomplete game earns points. These are product rules needed by the engine contract.
4. Resolve evening scoring. The historical engine contract has N-to-1 placement points, whereas current prototype decisions explicitly leave conversion unresolved. Settle team outcomes for Impostor, ties, absent players, differing group sizes and one award per completed game. Never add raw Categories and Bluff points directly.
5. Playtest replayable content and pacing. Current fixed letter B, Lantern and octopus question validate screens only. Try several representative rounds with a small group. Specifically measure Categories host review effort (four categories times twenty players is eighty judgments) and Bluff reading/voting burden at twenty answers. Decide realistic per-game limits from that evidence.
6. Specify Categories dispute resolution and input semantics, plus Bluff truth equivalence, duplicate lies and missing answers. Retain simple rules unless playtesting justifies more phases. Decide how drafts reach the server before a remote Stop; a locally typed but unsent answer must have a defined outcome.
7. Document the existing shared UI patterns as component contracts: screen shell, fixed actions, constrained scrolling, preparation, waiting, choice/confirmation, result and details dialog. Add pending/saved/failed submission and reconnect states. Hide scroll rails only while preserving reachability and an understandable indication of additional content.
8. Keep a concrete physical-device gate: Android and iPhone, docked keyboards, long names/80-character answers, small heights, large text, keyboard/screen reader access, refresh/background/rejoin. UI fixtures and VM tests cannot close this gate.

## Doplay: useful patterns and limits

Links below are pinned to the inspected revision; findings describe source behavior, not a live certification.

- [Session store](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/lib/store/session.ts): remembers nickname, avatar and active room with versioned migration. Adopt the convenience pattern; persist preferences separately from authoritative game state and authenticate room recovery on the server.
- [Connection bar](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/components/ConnectionBar.tsx): concise disconnection/recovery feedback with a status announcement. Its signal is browser online/offline, so Playai should additionally reflect the actual server connection and acknowledged submission. Keep Playai's visual tokens.
- [Game shell](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/components/game/GameShell.tsx) and [runner](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/lib/server/game-runner.ts): action IDs and server-side duplicate checks are useful. Playai should additionally scope requests to game/round/phase and retain the same ID when retrying a logical submission. The shell distinguishes finishing with results from aborting; settle that semantic distinction across Playai games.
- [Wake lock](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/hooks/useWakeLock.ts): requests screen wakefulness and reacquires on visibility return. This is already planned in Playai; carry it into device acceptance rather than presenting it as a new architectural idea.
- [Categories engine](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/games/panstwa-miasta/engine.ts): excludes used letters until its pool is exhausted; supports player challenges, justification and a timed vote. Borrow nonrepeating content selection. Treat challenge voting as a playtest candidate, not an automatic replacement for accepted host review. Its grace period and 15-point special case are different rules, not proven improvements.
- [Client ticks](https://github.com/w84kubus/doplay/blob/c36c39182e010df38eda9e51c5acc237673c7bac/src/hooks/useGameTick.ts): host nudges timeouts, other clients provide delayed fallback. Do not import this dependency; Playai's existing server-alarm decision addresses phase progression independently of browsers.

Since the previous d7a9bef inspection, Doplay added a Ludo game and bot support, among other changes. These expand scope and do not address Playai's current readiness priorities. Do not import its visual accents, settings matrix or additional games merely for parity.
